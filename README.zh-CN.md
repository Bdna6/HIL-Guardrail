# HIL — Human in the Loop（人在回环）

**把执行交给 AI，把理解、判断与责任留给自己。**

[English](README.md) · 简体中文 · [本地后台上手](docs/10-local-runtime.zh-CN.md)

HIL 是一个本地后台运行的人机协作护栏。用户通过网页配置模式和边界，工作、提问与学习始终在原 CLI / IDE 中完成。HIL 帮助人们有意识地委托 AI：明确哪些工作可以交给 AI，哪些判断、验证与思考需要由人保留，并在关键节点帮助人履行这些责任。

我们默认用户主动选择 HIL，希望改善自己的协作与学习过程，不以防止用户另开工具绕过 HIL 为目标。

## 为什么做 HIL

- **构建项目：**没有编程基础的新手，难以判断 AI 推荐的依赖、权限和云服务是否必要。本地应用可能在不知情中变成复杂的云端项目。
- **完成工作：**AI 的便利可能逐渐取代人工判断与核验，未经检查的成果被直接提交，直到发生事故才恢复审查。
- **学习知识：**把题目整体交给 AI 可以获得答案，却可能失去练习思考的过程。渐进提示、解释与变式挑战可以帮助用户建立理解。

我认为需要解决的核心问题是：**人是否知情、是否作出必要判断，并理解和验证需要负责的结果？**

## 产品方向

| 模式 | 主要目标 | 典型介入 |
| --- | --- | --- |
| 构建 | 控制项目范围，理解技术选择 | 新依赖、外部服务或需求扩展前解释影响并确认 |
| 工作 | 让关键结论与交付有据可查 | 追溯来源、检查假设、完成关键验证 |
| 学习 | 保留需要亲自完成的思考 | 先尝试，再提示；通过解释、预测与迁移应用回顾理解 |

信任边界扩展为**委托边界**：

1. **资源边界：**可以引入哪些库、服务、权限与数据连接？
2. **范围边界：**可以自行改变哪些需求与方案？
3. **责任边界：**哪些判断、核验与思考由人保留？

信任某个工具，不等于当前项目一定安装，也不等于用户理解使用的后果。陌生依赖不等于不安全；HIL 应说明证据和影响，不做无依据的安全裁决。

```text
明确目标与委托约定 → AI 分阶段执行 → 关键决策解释
        → 用户选择 / 核验 / 理解挑战 → 项目回顾与接手
```

挑战不作为所有场景的默认交互：技术选择需要解释，工作成果需要核验，学习目标需要思考与应用。理解挑战不能替代事实核查或测试，也不能准确证明一个人已掌握全部知识。

## 使用本地后台（0.2.0）

需要 Node.js ≥ 22.13 和可正常使用的 Claude Code。以下命令在项目根目录执行。

```powershell
npm install
npm run build
npm run hil -- install --scope user
npm run hil -- start --port 4174
```

打开 **http://127.0.0.1:4174/local/dashboard**，可实际修改模式、开关与策略；关闭网页后后台继续运行。在 Claude Code 中直接询问“HIL 当前模式、是否启用及版本号”，由 hooks 提供真实状态。

- 安装后新开 Claude Code 会话；之后模式修改在下一条用户消息时生效，关闭开关对后续工具事件立即生效。
- 默认只启用本地规则和人工检查点。使用 API 地址、模型和密钥配置时，可在启动命令追加 `--semantic claude`，允许额外的模型评估并消耗该供应商额度。**不能复用 Claude 官方账号登录 / 订阅额度或 OAuth 凭据**；只有订阅登录时不要加该参数。`--direct` 是可选直连方式，需要代理时不要加。
- `npm run hil -- runtime status` 查看实际状态；`npm run hil -- stop` 停止后台。
- 云账户尚未接入，本地控制台不要求登录；原 `/demo/dashboard` 继续使用独立浏览器样例数据，不能控制真实 CLI。
- `npm run dashboard` 仍只启动静态 demo（默认 4173），不启动后台。

完整流程、数据范围、CC Switch / DeepSeek、检查点边界和实测结果见 [本地后台使用说明](docs/10-local-runtime.zh-CN.md)。

## HIL 如何参与 CLI 工作

采用 **本地伴随程序 + 网页控制台 + 工具适配器**。当前控制台配置本机全局模式与目标，本地服务保存约定；会话分别登记加载的 revision，适配器通过官方接口接收事件、传递上下文并执行可支持的检查点。

- **伴随模式：**保留原 CLI 工作流，提供解释、操作检查点与阶段回顾。
- **学习模式：**通过适配器加载学习约定，在原 CLI / IDE 对话中尝试、获得提示并完成理解检查；不另建网页 Agent。

当前流程：网页保存模式 → 下一条用户消息时适配器加载并注入状态 → 在原工具继续。首次安装 hooks 后需新开会话。网页保存不等于 CLI 已生效。操作审批、理解评估和输出展示是不同能力，需要分别验证。原生 CLI 的结束检查点不等于能在答案显示前拦住答案。

## 已实现能力的边界

确定性规则本地处理，无遥测；会话状态临时保存。启用语义评估后，必要任务、操作与回答片段会发给配置的模型服务，常见密钥字段脱敏；不应假定脱敏能识别所有敏感内容。详情见本地后台说明。

- Build / Work / Study 的提示、摘要、上下文和确认偏好会提供给 Agent；它们并不都是独立的强制闸门。
- 硬检查点主要覆盖已识别资源、Study 实现前参与和有变更后的阶段回顾。语义范围判断与理解评估需要额外模型配置。
- 未配置评估时，实质性回答仅记为参与/授权，不证明理解；模型的提示遵循和评估结果也不能保证正确。
- 暂未实现网页中的项目级模式、云账户/同步、长期项目记忆、真实 Usage 统计及 Codex 适配。

## 后续工作

1. 用原型验证新手能否理解模式、决策说明和检查点。
2. 扩充不同 Claude Code 版本与 DeepSeek 原生会话的兼容性验证。
3. 改进语义评估准确性、误报控制与更丰富的项目证据。
4. 建立正式账户认证与用户选择保留的项目记录。
5. 接入 Codex hooks。

HIL 不做员工监控、参与度排名或“人类贡献百分比”。产品验证关注用户是否发现重要选择、完成关键核验、能够解释和接手成果，以及干预带来的打扰。
